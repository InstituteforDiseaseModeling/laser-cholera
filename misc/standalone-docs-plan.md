# Standalone documentation plan for `laser-cholera`

## 1. Goals and non-goals

**Goals**

- Make `laser-cholera` usable end-to-end by someone who has **never touched the upstream R [`MOSAIC`](https://github.com/InstituteforDiseaseModeling/MOSAIC) package**. Today the documentation assumes MOSAIC drives parameter construction; we need a parallel path for direct callers.
- Give every field in `default_parameters.json` a documented purpose, shape/dtype, valid range, and — critically — **the value that turns the feature off**.
- Provide three working starter configurations that span the spectrum we actually care about:
  1. A **single-location** toy run (no mobility, no spatial structure, every optional feature off).
  2. A **single country, multi-admin (admin1 or admin2)** run (mobility on, country-internal structure).
  3. A **Sub-Saharan Africa country-level** run (the existing baseline; what the bundled `default_parameters.json` already targets).
- Anchor the work to the [Diátaxis](https://diataxis.fr) framework so the four documentation kinds stay separate and we know what each page is for.

**Non-goals (this round)**

- Re-deriving or re-validating the model science. We document what the parameters mean operationally; the math is the existing model.
- Building a parameter-construction GUI / wizard.
- Documenting MOSAIC itself. We link out; we do not duplicate.
- Translating the upstream R reference. We continue to point at `reference/` only as a cross-check.

## 2. Audiences

| Audience | Primary need | Where they land first |
|----------|--------------|----------------------|
| MOSAIC user who just wants to run the bundled defaults | `metapop --seed …` and "what comes out" | Existing `docs/usage.md`, lightly extended |
| Researcher swapping in their own data (admin1/admin2, custom country) | Parameter reference + minimal-config recipe + shape rules | New "Configuring laser-cholera" how-to and the Parameter reference |
| Modeler experimenting with one feature in isolation (turn on vaccination, turn off mobility, …) | "What does X do, and what's the off-value?" | Per-feature how-to pages + Parameter reference |
| Developer hacking on the package | API ref, model explanation | Existing autogen API ref + new Explanation pages |

## 3. Diátaxis mapping

The four Diátaxis quadrants and what we put in each:

- **Tutorials** *(learning-oriented; hand-held)*
  - `tutorials/first-run.md` — install, run defaults, look at outputs. ~10 min.
  - `tutorials/single-location.md` — build a single-patch SEIRV config from scratch, every optional feature off; one tick at a time; introduces the parameter vocabulary.
  - `tutorials/multi-location-country.md` — extend the single-location config to N admin units in one country; turn on mobility, see emigration in the trajectories.
- **How-to guides** *(task-oriented; "I already know what I want")*
  - `how-to/override-parameters.md` — CLI `--over` and Python `mods` (already covered in usage.md; move + extend).
  - `how-to/enable-vaccination.md` — set `nu_1_jt` / `nu_2_jt`, choose `phi_1` / `phi_2`, decide on `omega_1` / `omega_2`.
  - `how-to/configure-mobility.md` — `tau_i`, `mobility_omega`, `mobility_gamma`, and what `tau_i = 0` means.
  - `how-to/enable-seasonality.md` — `a_1_j` / `b_1_j` / `a_2_j` / `b_2_j` / `p` and the inert-form `(a_1_j, b_1_j, a_2_j, b_2_j) = (0, 0, 0, 0)`.
  - `how-to/calibrate-and-score.md` — `calc_likelihood`, the four shape weights, `reported_cases` / `reported_deaths`, `epidemic_peaks`. Folds existing usage.md content.
  - `how-to/scenario-builder.md` — point at `metapop/scenario.py` (programmatic config from a small handful of high-level knobs).
- **Reference** *(information-oriented; authoritative)*
  - `reference/parameters/index.md` — table of every parameter (name, shape, dtype, range, default-on/off, "what feature it controls"). Source-of-truth for "is this required?".
  - `reference/parameters/<group>.md` — one page per parameter group (see §5). Each parameter gets: definition, shape, dtype, valid range, what value disables the feature it gates, link to the model section that uses it, citation back to `default_parameters.json` and `validate_parameters`.
  - Existing autogenerated `reference/` (mkdocstrings over `src/`) — unchanged; we just link into it more heavily.
- **Explanation** *(understanding-oriented; the model)*
  - `explanation/model-overview.md` — compartments (S, E, I_sym, I_asym, R, V1, V2), tick cadence, where each component plugs in.
  - `explanation/transmission.md` — force-of-infection split (`humantohuman.py` + `envtohuman.py` + `environmental.py`); how `beta_j0_hum`, `beta_j0_env`, `theta_j`, `kappa`, `decay_days_*`, `zeta_*` combine.
  - `explanation/seasonality.md` — two-mode harmonic; what the `a_*`, `b_*`, `p` parameters do.
  - `explanation/mobility.md` — the gravity-model coupling `pi_ij`; the role of `tau_i`, `mobility_omega`, `mobility_gamma`; what falls out at single-patch.
  - `explanation/reporting-and-likelihood.md` — `rho`, `rho_deaths`, `delta_reporting_*`, observed-vs-estimated, the NB core, the four shape terms.

The Reference quadrant is the load-bearing one. Everything else can link into it; it has to be navigable on its own.

## 4. The "minimal configuration" strategy

Rather than ship a separate `minimal_parameters.json`, we document **how to derive a minimal config from `default_parameters.json` by setting the right fields to their inert values**. This keeps a single source of truth and makes "turn feature X on" a one-line override rather than a re-baseline.

Inert values, by feature (these are the off-switches the documentation pages will reference; the Reference pages give the authoritative list):

| Feature | Off-value | Notes |
|---|---|---|
| Vaccination (dose 1 + dose 2) | `nu_1_jt = 0`, `nu_2_jt = 0` over the whole window; `V1_j_initial = V2_j_initial = 0` | `phi_1`, `phi_2`, `omega_1`, `omega_2` then have no effect |
| Human-to-human transmission | `beta_j0_hum = 0` (vector of zeros) | Disables `HumanToHuman` term |
| Environmental transmission | `beta_j0_env = 0` (vector of zeros) | Disables `EnvToHuman` term; `theta_j`, `kappa`, `decay_days_*`, `zeta_*`, `psi_jt` then irrelevant |
| Seasonality | `a_1_j = a_2_j = 0`, `b_1_j = b_2_j = 1` (any non-zero), `p = 365` | Seasonal multiplier collapses to constant 1.0 |
| Mobility / coupling | `tau_i = 0` (vector of zeros) | Patches do not exchange exposure; `mobility_omega` / `mobility_gamma` still required by validator but unused |
| WASH protection | `theta_j = 0` (vector of zeros) | No WASH effect on env transmission |
| Vital dynamics (closed population) | `b_jt = d_jt = 0` over the whole window | No births / non-disease deaths |
| Waning natural immunity | `epsilon = 0` | R → S waning disabled |
| Waning vaccine immunity | `omega_1 = omega_2 = 0` | V1/V2 → S waning disabled (paired with vaccination off) |
| Asymptomatic split | `sigma = 1` (all symptomatic) or `sigma = 0` (all asymptomatic) | Pick the simpler half |
| Reporting under-reporting | `rho = rho_deaths = 1` | Observed = estimated |
| Reporting lag | `delta_reporting_cases = delta_reporting_deaths = 0` | No tick offset |
| Epidemic vs endemic regime switch | `chi_endemic = chi_epidemic = 1.0`, `epidemic_threshold = 0` (or large) | One regime everywhere |
| Likelihood scoring | `calc_likelihood = False` (or all four `weight_*` = 0 and `calc_likelihood = True`) | No LL computation; or NB core only |
| Environmental forcing curve | `psi_jt = 1` everywhere; `psi_star_*` constants set to match | Constant environmental suitability |

A few cases need a note:

- `b_1_j` / `b_2_j` being zero would divide by zero in the seasonal harmonic — the off-trick is to zero the *amplitudes* (`a_*`), not the periods. Reference page must spell this out.
- `mobility_omega` / `mobility_gamma` are required by `validate_parameters` even when `tau_i = 0`. Document that they remain valid but have no effect.
- `epidemic_peaks` can be omitted entirely when `weight_peak_*` are zero; the validator only checks columns *if* the field is present.
- `nu_jt_sources` is a free-text-ish field. Treat as documentation, not a knob.

## 5. Parameter taxonomy (groups for §3 Reference pages)

Grouping all ~70 top-level fields in `default_parameters.json` into pages we can write and a reader can scan:

1. **Run identity & calendar** — `seed`, `date_start`, `date_stop`, `location_name`.
2. **Initial compartment populations** — `N_j_initial`, `S_j_initial`, `E_j_initial`, `I_j_initial`, `R_j_initial`, `V1_j_initial`, `V2_j_initial`, plus the `prop_*_initial` proportions.
3. **Vital dynamics** — `b_jt`, `d_jt`, `mu_j_baseline`, `mu_j_slope`, `mu_j_epidemic_factor`, `mu_jt`.
4. **Vaccination** — `nu_1_jt`, `nu_2_jt`, `phi_1`, `phi_2`, `omega_1`, `omega_2`, `nu_jt_sources`.
5. **Disease progression** — `iota`, `gamma_1`, `gamma_2`, `epsilon`, `sigma`.
6. **Reporting** — `rho`, `rho_deaths`, `delta_reporting_cases`, `delta_reporting_deaths`, `reported_cases`, `reported_deaths`.
7. **Regime switching** — `chi_endemic`, `chi_epidemic`, `epidemic_threshold`, `epidemic_peaks`.
8. **Geography & mobility** — `longitude`, `latitude`, `tau_i`, `mobility_omega`, `mobility_gamma`.
9. **Human-to-human transmission** — `beta_j0_hum`, `a_1_j`, `a_2_j`, `b_1_j`, `b_2_j`, `p`, `alpha_1`, `alpha_2`, `beta_j0_tot`, `p_beta`.
10. **Environmental transmission** — `beta_j0_env`, `theta_j`, `psi_jt`, `psi_star_a`, `psi_star_b`, `psi_star_z`, `psi_star_k`, `zeta_1`, `zeta_2`, `zeta_ratio`, `kappa`, `decay_days_short`, `decay_days_long`, `decay_days_spread`, `decay_shape_1`, `decay_shape_2`.

Each group page follows a fixed template (see §8).

## 6. Three worked configurations

We ship three configurations under `docs/configurations/` (and the JSON / Python snippets they reference under `docs/configurations/code/`). Each one is reproducible — the `python3 -m laser.cholera.metapop` (or `metapop`) command at the top of the page runs and produces the artifacts the page screenshots.

### 6.1 Single-location toy

- **Shape**: `len(location_name) == 1`, `nticks ≈ 365`.
- **What's on**: human-to-human transmission, default waning, symptomatic/asymptomatic split.
- **What's off**: mobility (`tau_i = 0`), environmental transmission (`beta_j0_env = 0`), vaccination, seasonality, WASH, reporting noise (`rho = rho_deaths = 1`), likelihood scoring.
- **Purpose**: prove the install works, illustrate the parameter shape conventions in the simplest possible setting, give the reader something they can mutate in 30 seconds.

### 6.2 Single country, multi-admin

- **Shape**: `len(location_name) = N` admin1 or admin2 units of one country (Mozambique or DRC are good candidates — large enough to be interesting, small enough to keep the JSON readable).
- **What's on**: mobility (gravity), seasonality, environmental + human-to-human transmission.
- **What's off**: vaccination (until we extend the tutorial), regime switching (`chi_endemic = chi_epidemic`).
- **Purpose**: show how the per-patch vectors and (T, J) matrices scale; show what `pi_ij` does to a single seeded outbreak.
- **Data source**: link to where we expect admin polygons + populations to come from (worldpop, GADM); we do *not* ship admin1/2 data, but we ship one synthetic example.

### 6.3 Sub-Saharan Africa, country level (baseline)

- This is what the bundled `default_parameters.json` already encodes. The configuration page is essentially "open the defaults, run, see this".
- **Purpose**: anchor the other two configurations; document the assumptions that go into the bundled defaults (date window, country set, calibration source).

## 8. Authoring rules

These are the rules every new page follows. The point is that one author or one model writing one page produces a result that looks like every other page.

**Parameter group pages** (`reference/parameters/<group>.md`)

For each parameter:

```
### `<name>`

- **What it controls**: one sentence.
- **Shape**: e.g. `(nticks, npatches)` or `scalar` or `(npatches,)`.
- **Dtype**: e.g. `float32`.
- **Range**: e.g. `[0, 1]` (validator-enforced) or `>= 0` (validator-enforced) or `unconstrained`.
- **Default behaviour**: link into the relevant Explanation page section.
- **Off-value**: the inert setting, e.g. `nu_1_jt = np.zeros((nticks, npatches))`.
- **Cross-refs**: the components that read it (`susceptible.py`, `envtohuman.py`, …) and the related parameters.
```

The validator (`validate_parameters` in `params.py`) is the source of truth for the **Range** field — every range claim in the docs must trace back to an `assert` in that function.

**How-to pages** follow the canonical Diátaxis shape: a single goal in the title, a numbered steps list, a single working code block at the bottom that the reader can paste, no detours, no "you might also want to".

**Tutorial pages** keep one continuous narrative. They build a config from scratch by importing `get_parameters` with `mods`, then progressively turning features on.

**Explanation pages** carry the math (LaTeX is already enabled in mkdocs via `pymdownx.arithmatex`) and the component-level diagrams.

## 9. Validation & QA

- **Doctest-able snippets**: any Python block that reads `>>> from laser.cholera…` runs as part of `pytest --doctest-glob='docs/**/*.md'`. We add a tox env for this so CI catches drift.
- **Config files run**: each of the three configurations under `docs/configurations/code/` is executed by a `tests/test_docs_configurations.py` smoke test that runs the model for ~30 ticks and asserts the model returns. This catches "the docs example silently broke" before users do.
- **Parameter inventory is complete**: a test in `tests/test_docs_param_coverage.py` reads `default_parameters.json`, the union of `scalars`/`arrays` lists in `dict_to_propertysetex`, the validator's asserts, and the Reference group pages, and fails if any key is documented in zero or two places.
- **Link check**: `mkdocs build --strict` already fails on broken links; CI runs it.

## 10. Phasing

Five waves, each independently mergeable. Stop and re-scope after each.

1. **Wave 1 — Scaffold + Reference.** Add the directory layout, add `nav:` to `mkdocs.yml`, write all ten Parameter group pages, add the param-coverage test. No tutorial / how-to / explanation content yet; pages exist as stubs with "coming in wave N". The site immediately becomes navigable and the reference is the new source of truth.
2. **Wave 2 — Three configurations.** Author the three JSON configs, the three configuration-page narratives, and the smoke test that runs each.
3. **Wave 3 — Tutorials.** First-run + single-location + multi-admin. Doctest-validated.
4. **Wave 4 — How-to guides.** Six task-oriented pages. Each one references back to the relevant Reference page and Configuration.
5. **Wave 5 — Explanation.** The five model pages. Carries the math; cross-links from Reference into here.

Inside each wave: parameter group pages, how-to pages, etc. are independent and can be fanned out across multiple PRs.

## 11. Open questions

- **Where do admin1/admin2 starter datasets come from?** Configuration 6.2 needs *some* coordinates + populations. Option A: ship a small synthetic example committed under `docs/configurations/code/`. Option B: point at an external dataset and provide a script that downloads + normalizes it. Recommend A for v1 (reproducibility), B as a follow-up.
- **Should `scenario.py` be a Reference page or a How-to?** It currently isn't documented at all. Treat as How-to in wave 4 and decide whether to elevate later.
- **`epidemic_peaks` in-window filter**: the recent change (`f8e3b38 Port R upstream's in-window peak filter`) shifted behaviour. Reference page must reflect the post-port semantics, not pre-port.
- **Visualisation parameters** (`visualize`, `pdf`, `quiet`): these are run-time toggles that `get_parameters` fills in with defaults. Document under "Run identity & calendar" or under the CLI flags section? Recommend the CLI flags section in `how-to/override-parameters.md` since that's where people will look.
- **MOSAIC linkage**: do we want a single "interoperating with MOSAIC" how-to page that documents the schema MOSAIC writes, or do we leave that to MOSAIC's own docs? Recommend a one-page stub that links out and says "MOSAIC's JSON is a valid `paramsource` — pass the path to `get_parameters`".
- **Default seed**: usage.md mentions `--seed 20240101` but the CLI default is `20241107`. Pick one canonical default and use it everywhere.

## 12. Definition of done

- Every parameter in `default_parameters.json` is referenced by exactly one Reference group page.
- Every parameter has a documented off-value (or a documented note explaining why it doesn't have one).
- `mkdocs build --strict` is green.
- All three configurations run end-to-end via the smoke test.
- Doctest CI is green.
- `docs/index.md` carries three labelled audience tracks ("I want to run defaults", "I want to swap in my data", "I want to understand the model") that funnel into the right quadrant.
